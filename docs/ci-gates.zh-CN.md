# 333 工作流门禁与维护约定

当前 PR 的检查以真实源码和测试执行记录为依据，按以下路径闭环：

1. `ci-test-matrix.yml`：一次构建并产出发行程序；Node / Bun 核心测试和六个补充测试分片并行执行，最终统一汇总，任一失败均阻断合并。
2. `dev-quality.yml`：独立检查跨平台开发工具、Lint、类型差异、原生加载和高危依赖。
3. `independent-models.yml`：按当前支持的直接 API 服务商，跨 Linux、macOS、Windows 验证工具、流式字段、认证及缓存迁移。
4. `independent-product-cleanup.yml`：检验品牌清理、隐私边界和通用 GitHub 审查入口。
5. `rebuild.yml`、`latest-stable-six-host.yml`：源码重建、六架构发行与运行；原版功能对照使用固定 2.1.317 基准。
6. `codeql.yml`、`upgrade-protection.yml`：安全分析、锁文件、MCP v2 和生产能力防回退。

旧 PR7 / M1 迁移与源码回写工作流已经完成历史任务，正式门禁保留对其实际功能的测试。其源代码、测试和必要研究资料留在仓库，由全量测试矩阵自动覆盖未列入核心测试脚本的测试文件。

## 测试登记规则

`build/run-unregistered-tests.mjs` 只将 `package.json` 的测试命令和可在 PR 实际触发的 GitHub Actions `run` 命令计作登记。旧分支绑定、路径过滤与注释不计为执行。CI 的 `--ci-supplemental` 模式覆盖 **所有不在核心脚本内的测试**，并可按 `--shard-count` / `--shard-index` 稳定分片。

实际测试失败、取消或未执行均不得标记为验收成功。需要排查时以 Actions 每个步骤和原始日志为依据，最终只按当前提交 SHA 的全量门禁作合并判断。

## 维护原则

- 新功能必须添加对应测试，并保证核心脚本或补充测试矩阵能够实际执行。
- 功能退役时同步删除旧专用工作流及无关的协议对照，保留必要的退役防回归。
- PR 工作流使用累计变更范围判断是否应触发。进入工作流后执行真实检查，不使用最后一次提交的差异直接跳过核心步骤。
- 独立的矩阵任务尽量并行；需要共享发行包时先构建一次，再以 artifact 分发；最终聚合任务严格检查所有依赖任务的结果。

## PR19 门禁改造与固定基准

- 官方原版对照工作流从 PR head SHA 检出，修复把 PR 编号当作 Git 引用的错误；原版 2.1.317 校验仍按哈希与真实运行执行。
- `m1-public-lock-sync.yml` 改为只读锁文件验收，锁文件通过提交和评审维护，工作流不再自动推送变更；正式 `package.json` 版本、锁文件根节点版本和历史升级保护必须一致。
- 对锁文件确有必要的依赖升级逐条在历史基准 `approvedChanges` 留下原值、新值、技术原因、测试和 PR 证据，保留 SHA 校验、MCP v2、功能编号及六宿主门禁。
- `ci-gate-audit.mjs` 拦截数字 PR 引用、自动推送锁、退役 Ultrareview CLI 对照以及全量测试失去聚合的情况；`/review` 通用审查保持现行测试。
