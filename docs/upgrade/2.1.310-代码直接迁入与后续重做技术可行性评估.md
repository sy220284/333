# 333：Claude Code 2.1.310 代码直接迁入与后续重做技术可行性评估

> 目标：技术优先，尽可能复用现有有效实现，减少第一轮无意义重建；后续通过稳定接口逐步替换高耦合模块。**本研究原先只对比旧源码提取树与新版反编译模块；现已依据 `main@4868d5d` 的独立构建成功修正实施选择。** 此文档保留原模块扫描和载入测试的历史证据，具体执行以[最新完整方案](./2.1.310-全面升级方案.md)及[独立缺口清单](./2.1.310-升级缺口与逐项核查清单.md)为准。

## 一、结论与迁移方式

**最新 main 后的优先顺序：继承已独立构建的 2.1.88 TypeScript 核心 > 恢复旧版已存在但目标版仍需的功能 > 通过实测直接复用低耦合新版模块 > 对高耦合功能按可观察语义重写。原版 2.1.310 程序用于行为对照/可选进程适配，不能成为默认运行依赖。**

| 技术方式 | 当前判断 | 适用范围 | 需要验证的关键条件 |
|---|---|---|---|
| 原始 2.1.310 Linux x64 可执行程序原样运行 | **已通过 --version / --help**；具备进程级接入基础 | 作为短期参照后端，供 333 调用 CLI/headless/流式接口；同时是差分验收基准 | 身份认证、模型请求、持续会话、输入输出协议、权限/取消/恢复尚需在实际环境验收 |
| 单独搬迁低依赖模块 | **部分已实际导入**；可以先迁入调用边界清晰的纯函数/常量/数据处理模块 | 字符串、简单工具函数、协议数据与常量 | 逐个检查隐性全局变量、Node/Bun 语义、初始化副作用，执行单测和错误路径 |
| 连同依赖搬迁 Agent、Workflow、Review | **仅有完整文件集合和静态依赖证据，未验证独立运行** | 需要本地控制执行的核心能力 | 修复 Bun 编译路径、动态加载器、ES 资源管理语法、原生附加模块、运行时配置、权限/状态消费者 |
| 将全部反编译 JS 覆盖 333 旧版 TypeScript | **不可直接替换** | 无 | 新版模块为 Bun 编译后的产物，命名/模块边界与旧版 Source Map TypeScript 不一一对应 |
| 独立重做特定内部实现 | **有明确必要，但可延后** | 跨提供商模型能力、本地 Ultra 级审查、需要独立维护的稳定核心 | 必须依据新旧版本行为、权限、事件协议及可重复测试实现，逐步替换已有后端 |

**按最新主线修订的短期建议**：保留已通过三平台测试的 `src/native/build/tests` 与 Bun 编译，直接对比 2.1.310 的行为差分。原版程序保留为测试标杆，只有当明确需要隔离外部兼容入口时才启用进程适配器；低耦合模块先单独运行测试后复用，高耦合功能在原有核心中增量重写，避免先做整套原版进程后端再拆除。

## 二、实际模块文件与依赖统计

分析对象：`package/04_逐模块可阅读JavaScript/` 的**顶层 2,550 个 JS 文件**（2,547 个 `chunk-*.js`、`cli.js`、`audio-capture.js`、`clipboard-napi.js`），共约 **58.99 MB** JS 代码；另有 `src/plugins/functionHooks/hooks-worker/hooks-worker.js` 以及 42 份额外解压脚本文件，未混入顶层模块统计。旧版 Source Map 提取的 `source/src` 有约 **1,902** 份源文件，属不同类型的产物。

| 指标 | 实测值 | 解释 |
|---|---:|---|
| 顶层 JS 模块 | 2,550 | `chunk`、CLI 与两个原生模块装载代理 |
| 内容中出现 `/$bunfs/root/` 的模块 | 2,346 | 源码仍与 Bun 编译后虚拟文件系统路径耦合 |
| 文件中有具体 `/$bunfs/root/*.js` 字面引用的模块 | 2,344 | **不能按单文件孤立迁入** |
| 当前扫描无 BunFS JS 字面依赖的文件 | 206 | 只是独立候选，仍可能有 Node/Bun API、模块外状态或原生资源依赖 |
| 其中体积不小于 1 KiB | 99 | 优先做候选模块的实际导入与功能单测 |
| 其中体积不小于 8 KiB | 18 | 警惕大型第三方库虽无内部依赖，仍可能存在其他运行要求 |
| 使用 `import.meta.require` 的文件 | 113 | 包含运行时动态模块加载，单靠静态 import 解析不足 |
| 代码中含 `Bun.` API 调用的文件 | 43 | 需要 Bun 运行语义或接口适配 |
| 实际存在 `using/await using` 资源管理语法的模块 | 44 | Node 22.16 对部分路径执行存在解析限制 |
| `/$bunfs/root/` 非 JS 路径引用 | 247 个独立文件名 | 涉及资源、脚本和两个 `.node` 原生扩展 |
| 原生 `.node` 引用 | `audio-capture.node`、`clipboard-napi.node` | **当前可阅读 JS 提取目录未包含这两个二进制文件** |

依赖口径必须区分：

- **静态 ESM import**：只计算可以直接识别为 import/export 的边；会漏掉动态 require、Bun 运行时引用以及嵌在代码中的模块文件名。
- **完整字面路径依赖**：扫描各模块对 `/$bunfs/root/chunk-*.js` 的所有文件名引用，再计算传递闭包。它用于估算需要携带的文件上界，**不是实际执行时加载了这么多模块的证明**。

| 目标文件 | 顶层模块中的直接 BunFS JS 字面引用 | 传递可达文件 | 传递文件体积 |
|---|---:|---:|---:|
| `cli.js` | 92 | **2,542** | 约 58.93 MB |
| `chunk-2pjf4p7s.js`（Workflow） | 84 | **1,335** | 约 30.37 MB |
| `chunk-n7dvjfwp.js`（本地 Review） | 110 | **1,399** | 约 31.04 MB |
| `chunk-j0tbz6ra.js`（主指令等） | 533 | **1,335** | 约 30.37 MB |

Workflow 与 Review 依赖闭包交集 **1,335 个模块**；Review 多出的约 **64 个模块**是该依赖扫描口径下的特有部分。两个核心入口**共享大量底层代码**，单独复制某个 `chunk` 不等于复用一个完整子系统。

这组闭包统计来自静态文件名引用，其中可能包含条件分支、可选组件和仅用于装载的字符串。**用来决定搬迁风险，不可直接当作最小运行包规模。**

## 三、运行与加载实测

测试环境：Linux x64、Node.js `v22.16.0`；当前环境未安装独立 Bun CLI。原版 Linux x64 可执行文件实际执行：

- `claude-2.1.310-linux-x64 --version` → `2.1.310 (Claude Code)`。
- `--help` → 成功展示 CLI、`--print`、`--input-format`、`--output-format`、`--restricted`、`--safe-mode`、`--bg`、`--permission-prompts` 等已注册选项。
- **未执行真实登录/模型/代理/Workflow/Ultra 的端到端用例；只能算入口运行成功。**

对顶层 JS 直接使用 Node ESM `import()`：

| 文件 | 结果 | 证据 |
|---|---|---|
| `chunk-acd8w9vv.js` | 导入成功 | 成功返回 15 个导出符号 |
| `chunk-hpt4qf3e.js` | 导入成功 | 成功返回三个常量符号 |
| `chunk-rnxkk435.js` | 导入成功 | 成功返回 `wo` 符号 |
| `chunk-r8q2c9dc.js` | 导入且调用成功 | `qet('ab\\u0000cd')` 正确去除 NUL 字符 |
| `chunk-n7dvjfwp.js` | 导入失败 | `ERR_MODULE_NOT_FOUND`，引用了 `/$bunfs/root/chunk-2qx8pe6s.js` |
| `cli.js` | 导入失败 | `ERR_MODULE_NOT_FOUND`，引用了 `/$bunfs/root/chunk-qq3ygwcj.js` |
| `chunk-2pjf4p7s.js` | 导入失败 | `SyntaxError: Unexpected identifier '$e'`（加载依赖图含目标 Node 不支持的资源管理语法） |

独立 `node --check` 可通过部分入口文件，但**入口文件语法通过不代表传递依赖可加载**。上述四个小模块的成功导入也只证明当前进程下可执行相应模块加载路径，并不证明其全部业务边界。

Bun 官方文档说明 `/$bunfs/root` 是编译成单文件可执行程序后嵌入资源的路径。**安装独立 Bun 并不会自动为外部反编译目录生成该虚拟目录。** 若要以 Bun 直接运行文件，仍需要恢复/映射静态与动态导入、二进制资源和运行时初始化；本轮没有进行“独立 Bun 运行整包”的成功验收。

## 四、应当直接使用与应当延后处理的内容

### A. 可立即保留、原样运行

原版 Linux x64 可执行文件：版本和帮助入口已经验证，供行为比对和临时子进程接入。采用结构化输入输出与受限配置，在隔离工作区进行集成测试。**不把内置账户认证、云端服务、固定模型功能自动等同 333 自定义实现**；任何数据传输/权限都按实际参数和配置核验。

### B. 直接模块搬迁的优先候选

无内部 JS 路径依赖的纯函数、常量、字符串处理、简单数据转换。当前共 206 个静态候选，其中 99 个大小至少 1 KiB；已抽取四个完成导入抽测。逐模块用测试证实：输入/输出、错误、平台、外部副作用和实际消费者；通过后纳入 333 的独立包。

### C. 需要成组迁移与适配

本地工具、Provider、权限、状态管理、Agent 和 Workflow：首先保留编译模块间导入关系，建立受控的路径重映射和动态导入映射，补齐资源文件；在隔离进程验证实际 API 和异常，再决定哪些直接复用。

**不要把整套 2,550 个文件平铺覆盖 333 `src/`**：旧版 TypeScript 与新版打包 `chunk` 不具有相同的文件/函数职责映射，简单覆盖会破坏 333 的工程结构和测试路径。

### D. 无法从本地包“直接获得”的云端内部能力

新版普通本地 `/code-review` 有实际实现，可作为本地审查基线。云 Ultra 路径仍依赖远端 BugHunter/云会话服务；反编译包只提供本地启动、上传/控制/结果呈现相关代码，没有可在 333 直接加载的完整云端服务端深审内核。

本地 Ultra 级深审应复用已经可用的本地 Review/Agent/Workflow 接口，再补独立发现、真实复现、反证、证据合并、报告和安全隔离。

## 六、后续可持续重做的接口边界

建立四层关系，减少反复拆包：

1. **已有源码核心与参考程序分离**：生产入口继续调用 main 已经能独立编译的 `src`；原版 2.1.310 程序用同一套 `start/send/watch/cancel/resume/result` 行为合同做隔离差分。只有确有需求且显式选择时才使用原版进程适配器。
2. **独立任务/权限/工作区运行核心**：无论使用原版进程、已迁入 JS 还是未来重写模块，任务 ID、权限、取消和事件结构统一；确保 333 能替换后端而不重做 UI。
3. **可替换的功能提供者**：Agent、Workflow、Review、模型、工具按稳定接口注册；每一项支持 `native_process / imported_module / independent_impl` 的技术落位标识，由显式配置选择，禁止静默换后端或伪成功。
4. **单一行为验收库**：按同一份功能行为要求对照 2.1.310 参考程序与 333；记录实际实现和证据，今后改代码只需重跑受影响的测试及完整回归。

## 七、可复现检查与当前边界

- 模块依赖扫描：扫描反编译目录每个顶层 JS 的静态 import、`/$bunfs/root/chunk-*.js` 字面路径、`import.meta.require`、`Bun.` 与资源文件引用，按入口计算路径闭包；**闭包仅为依赖候选上界**。
- 运行检查：`node --version`、原版 `--version`/`--help`、对典型独立模块的 `import()` 及纯函数调用、对 Workflow/Review/CLI 的失败加载测试。
- **本轮未做**：独立 Bun 执行反编译整包、修复完整虚拟文件系统、所有单模块逐个运行、原生 `.node` 恢复、模型在线调用、多代理完整实测、84 项端到端签收。此分析是**迁入策略与实证分级**，不代表升级功能已交付。

**按最新主线修正后的最终技术选择**：在已独立构建且三平台通过测试的 `src` 上持续升级；原版 2.1.310 程序是独立对照基准，少量可独立运行的新版模块可直接复用；高耦合功能复用已有 Query/工具/权限/Agent 结构，按目标行为补齐。全部缺口与验收见独立清单。保留 M1–M10 内容，不为临时直搬重复建设后端。
