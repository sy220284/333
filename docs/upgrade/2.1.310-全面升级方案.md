## 0.1 升级目标与每项差异的落地闭环

**必须交付的主目标**：以当前 333 的 2.1.88 TypeScript 源码为唯一工程起点，对照 2.1.310 正式程序与反编译代码，将原功能的新增、增强、修复、参数变化、替换和退场逐项应用到旧源码；把新版独有的功能完整接入 333 的入口、权限、工具、状态、界面及运行链路。所有适用的新版功能最终都要可启动、可执行、可观察、可恢复并可实测。

**额外建设目标予以保留**：在版本对齐基础上完善整体架构、可替换模型适配、本地多 Agent、动态 Workflow、本地 Ultra 级深审以及跨平台体验。这些目标独立标记为 **333 扩展**；对齐项以 2.1.310 实际行为作为标准，扩展项以本方案的独立体验和质量测试作为标准。

**一个差异从发现到交付的固定路径**：

1. **找到功能**：借助 2.1.88 源码、2.1.310 反编译源码、6,313 条变更与开关索引确定入口和版本变化；优先用新旧程序实际触发功能，明确正常、异常、授权和恢复行为。
2. **检查旧版**：定位 333 现有功能函数、调用者、开关、界面和数据流，在相同条件下运行，确认是真缺失、行为落后、已具备，还是目标版已替换。
3. **修改旧版源码**：现有代码直接升级；源映射或新版可复用实现直接恢复、整合；缺失或高耦合部分按新版完整逻辑、接口和依赖关系重写；调整必要的架构以保证能力完整运行。
4. **接通完整功能链**：把入口、参数、模型、工具、权限、状态、持久化、UI/SDK 输出和失败恢复全部接到真实代码上，并清理过时分支和重复实现。

6. **完成后签收**：提交真实源码改动、差异测试、运行结果和变更映射；该功能达到目标行为后标记完成，随后继续下一项，直至全量完成。

**执行节奏**：M1 的核查与 M2–M9 的源码开发按能力逐项衔接、连续推进；发现一项真实差异就交由对应 M 修改并测试。90 种开关、61 项待补调用链和 6,313 条记录是检查覆盖范围和发现缺口的工具，**每一条适用差异最终都要指向源码处理结果与运行验收**。M10 汇总并复核整体完整度。

**交付判断**：完整交付以 333 的实际源码功能、完整执行链及新版行为对照通过为准；资料清单、静态定位、命令注册和测试方案本身属于过程成果。

## 1. 总体选择：以已构建主线进行终态差分升级，形成“单核心＋多入口＋能力插件”架构

**工程实际技术栈（2026-11-01 核查）**：沿用已通过 CI 的 **TypeScript + Bun 1.4.4 构建/发行体系及现有锁文件**，保留 `src/entrypoints/cli.tsx`、`build/`、`native/`、`tests/` 与 Linux/macOS/Windows 工作流。Node.js 可用于已验证的脚本/测试或明确需要的兼容接口；**以现有 Bun 主干持续构建和发布，并按实测收益决定是否调整 workspace**。未来确需更换打包运行时，必须先证明全量功能回归及跨平台行为无损，再单独实施。模型 Provider 通过可替换接口扩展，以模型能力协商驱动通用业务。

      ▼    ▼          ▼          ▼

## 2. 在现有工程内建立职责边界（按需拆分）

**工程约束**：继续使用已验证的 `src/`、`native/`、`build/`、`tests/` 与三平台 CI。下述 `packages/*` 等是职责划分的规划路径；实施前优先沿用当前目录，必要时按职责平滑迁移。优先在现有代码中统一任务/事件、模型、工具、权限、持久化和 Agent/Workflow/Review 的边界，确有收益且全部回归成功后再抽取包。

| 组件 | 职责 | 明确边界 |
|---|---|---|
| `apps/cli` | 命令、参数、headless、输入输出格式与进程退出 | 不直接实现工具业务 |
| `apps/tui` | 聊天、权限弹窗、任务树、Diff、会话切换、键盘/语音 UI | UI 不直接发模型请求 |
| `packages/runtime` | 事件驱动的 Agent 循环、调度、状态快照、取消/重试/恢复 | 任何工具执行必须经过 policy |
| `packages/protocol` | 消息、内容块、工具调用、结构化流、事件来源类型 | 适配器之间统一语义 |
| `packages/providers` | Claude/其他模型请求、流式解码、限流、usage、缓存/重试 | 保留厂商扩展字段，通用核心不受制于厂商 |
| `packages/policy` | 硬阻止/明确授权/自动允许、数据目的地、来源防伪、安全审计 | 执行授权由策略引擎和真实用户授权决定 |
| `packages/tools` | Read/Write/Edit/Glob/Grep/Bash/Git/Notebook/Web/浏览器等 | 每个工具有 schema、权限、超时、撤销和负例测试 |
| `packages/workspace` | 工作树、路径边界、沙盒、文件变更、Diff 与回滚 | 区分本地项目与共享远程资源 |
| `packages/session` | 会话持久化、历史重放、压缩、备份、故障恢复 | 恢复时根据持久化操作结果确认已完成动作 |
| `packages/context` | 项目指令、附件、提示词拼装、上下文窗口、缓存 | 用户指令/通知/外部材料分类型建模 |
| `packages/memory` | 记忆提取、召回、Dream 归并、过期核查 | 记忆不构成即时授权 |
| `packages/extensions` | MCP、技能、插件、Hook、扩展 API、兼容性验证 | 外部扩展最小权限和版本契约 |
| `packages/agents` | 可选协调者、Worker、Fork、Observer、子角色 | 默认单代理；用户明确授权才派生 |
| `packages/bridge` | IDE/远程/移动入口、WebSocket/SSE、重连/鉴权 | 网络来源与本地执行分离 |
| `packages/observability` | 事件追踪、资源统计、性能指标、脱敏日志 | 用户数据本地优先，遥测需明示与配置 |
| `native/` | 文件检索、图像、剪贴板、音频及其他平台能力 | 原生失败应报告具体不可用能力 |
| `tests/` | Mock/回放/参考行为差分/安全回归/端到端验收 | 验收记录可重复、可定位 |

当前 `src/` 与 `cli.js` 保留为**旧版行为基线**，逐项通过能力契约、最终源码证据与测试决定沿用、增强、替换或退场；对已符合目标的实现保留并增加回归；以实际能力缺口确定重写范围。新工程通过明确命名的目录补齐并接管。根目录仅保留标准元信息、workspace 配置、构建配置与项目入口，避免反复嵌套。

## 3. 核心功能升级决策

### 3.1 会话与模型执行核心（最高优先级）

- 基于统一状态机处理流式文字、思考块、工具请求、工具结果、部分 JSON、取消、续跑、重试、令牌计算和费用；工具结果必须与 tool-use ID 一一对应，避免丢块与重复执行。
- 每次有副作用的工具调用落盘记录 `request-id`、执行目标、批准人/批准来源、请求摘要、执行结果；进程重启时根据状态判定“未开始/已执行/结果未知”，未知状态先查证，杜绝重复写入、重复推送。
- 强制定义受支持模型的 capability profile（上下文窗口、流协议、思考块、图片、缓存、工具并发、结构化输出），用户可显式选模型，CLI/TUI/SDK 共用。
- 静态系统提示片段/动态上下文/项目指令/工具描述分开缓存。用回放检验模型输入顺序和来源。

### 3.2 工具与工作区

- 对已有工具逐项**保留并对齐最终语义**，按版本演进增加或调整 Read/Write/Edit/Glob/Grep、终端、Git、Notebook、Web、浏览器、PDF/图像、Monitor 等功能；以功能实现差异和实测改善登记完成进展。2.1.277 已删除 TaskOutput，目标版本改由 Read 读后台任务输出文件。
- 对 Read→Edit、文件路径边界、二进制、编码、超大文件、软链、并发修改、沙盒与终端信号分别建立测试；不允许以“工具进程返回 0”冒充功能正确。
- Git 写入采用改动集隔离，检查当前分支、现有用户变更、Diff、测试结果后提交；只暂存当前任务所属文件；公共 PR 标题/正文按项目要求生成中文。

### 3.3 安全与执行授权（新版最关键结构升级）

新版 `permissions_external-df98b90a.txt` 中确认 **21 个环境配置字段、1 条 HARD BLOCK、72 条 SOFT BLOCK、17 条 ALLOW 例外**（顶层条目计数）；与 2.1.88 的 5/29/7 单层模板结构有显著差异。重建时建立可测试规则数据表与确定性 `PolicyDecision`，另用分类器辅助判断复杂语义。

必须覆盖：外部文本伪造用户指令；后台通知/定时触发/Worker 回报被当成用户同意；删除范围未知；敏感信息通过终端、浏览器、Git/CI、外部网络流出；越权执行；流水线绕过；共享资源操作；受保护基础设施变更。授权等级由可信的用户授权和策略判定，外部文本始终按原始来源处理。

来源证据：`chunk-wany0nxw.js:520–554`（通知/定时标签）、`chunk-qg3fkqqr.js:64`（子代理回传）、`chunk-j0tbz6ra.js:52248,52435,52559,53142`（分类器及模板注入）。严禁简单复制庞大自然语言模板即宣称权限完成；规则须接上程序执行检查。

### 3.4 长任务、后台与多代理（按明确授权启用）

- 单代理默认可持续完成用户已授权且可恢复的工作；停机/额度/工具故障需记录剩余事项，恢复后先核对结果再继续，绝不承诺无法验证的后台进度。
- 工作树、临时目录、Git 分支/提交、工具进程和会话生命周期绑定；容器重启后旧进程状态变为“待核验”。参考 `chunk-j0tbz6ra.js:41825`、`chunk-4072fsq4.js:163`、`chunk-njrx31ky.js:85`。
- 协调者、Worker、Fork、Observer 分别定义角色、可用工具、写入空间、回传契约和失败交接；主代理必须独立验收 Diff/测试，对 Worker 返回结果独立核验文件、测试和运行结果；参考 `chunk-5qtb3hv4.js:99–320`、`chunk-f6dpayaf.js:34–73`、`chunk-28117reb.js:152–154`。
- **派生代理与定时任务由用户明确授权后启用**；后台事件保留原始来源，按本次用户授权范围执行。

### 3.5 上下文、自动记忆与主动交互

- 压缩须保留用户原话、不可变约束、操作已完成/未完成、文件位置、错误、待验收项和权限；恢复后按状态验证。参考 `chunk-j0tbz6ra.js:43349–43458`。
- 记忆类型分用户长期偏好、项目上下文和外部参考，过期信息以“待复核”标记；Dream 不自动改项目指令；参考 `chunk-d5zj5299.js:1822–1843`、`chunk-zsyd2kjt.js:48–105`。
- `/btw` 旧版已有；新版独立 “You should know”、一次性侧边提示、Artifact 评论读/写角色按触发条件接入，明确只读、一次性、只读状态准确呈现，实际修改以写入结果确认；参考 `chunk-k9eem9n9.js:490`、`chunk-c910wjkr.js:124`、`chunk-8x7w052f.js:1833`。
- 用户可感知交互：结构化执行计划、正在运行/等待授权/已验证状态，Diff 预览，一键恢复会话，错误定位与可操作建议；中文/英文界面可切换。
