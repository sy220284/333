# 333：云端多 Agent、动态 Workflow 和 Ultrareview 的本地化可行性与迁移方案

> 范围：将 2.1.310 中原本部署在云端会话/远端沙盒中的能力变为 **333 本地工作区运行的能力**，保留用户可观察的多代理执行、工作流、深度审查和结果验收。证据：333 main 的 2.1.88 提取源码、资料库 2.1.310 Linux x64 可读反编译包及 Anthropic 官方版本记录。本文属于**代码级可行性评估/验收设计**，并不代表本地功能已实现。

## 一、决策结论

| 功能 | 本地可迁移 | 已查明的代码事实 | 本地需补齐的主干 | 无法直接照搬的部分 |
|---|---|---|---|---|
| 多 Agent 协作 | **可，复用度较高** | 2.1.88 有本地 Agent、协作者模式、`spawnMultiAgent`、子代理执行器、任务表；2.1.310 继续增强 Agent 工具、工作树隔离、任务恢复 | 本地任务所有权、并发队列、角色权限继承、消息、独立工作树、结果验证 | 云会话的管理员控制台、云资源调度服务 |
| 动态 Workflow | **可，目标 2.1.310 已有本地路径** | `chunk-2pjf4p7s.js:445,511–519,887,990–1016,1694–1718`：`agent/parallel/pipeline/workflow`、`local_workflow`、agent 控制器、journal 和恢复；远程隔离根据构建/开关可不可用 | Workflow 运行器、步骤 DAG/并发依赖、任务日志、恢复时不重复执行、副作用审计、结构化输出 | 云同步的 Workflow journal、远程 Agent 隔离/云会话服务；它们不是本地运行的先决条件 |
| Ultrareview 深度审查 | **审查能力可本地重建；云端服务本身不能原样搬运** | 2.1.88 `src/commands/review/reviewRemote.ts:128–300` 调用 `teleportToRemote`，准备 PR/分支、云环境、`BUGHUNTER_*` 配置；2.1.310 `chunk-j0tbz6ra.js:33731–33732` 仍明确写着运行于 cloud session，`:34298–34319` 通过远端接口发布结果 | 在本地重新实现差异切分、并行审查、候选缺陷交叉复核、测试复现、去重排序、证据报告与可选 PR 评论 | 云端 BugHunter 编排脚本、托管任务系统、配额计费/远端组织认证、Anthropic 特有服务接口、未公开内部策略 |

### 复查补充：2.1.310 已有更强的本地审查，请优先迁移

2.1.88 `src/commands/review.ts:9–43` 已有简单本地 `/review`，云端 Ultra 独立注册。2.1.310 的 `chunk-n7dvjfwp.js:1080–1395` 已将本地审查扩展为 `/code-review`：多种强度、可选后台子 Agent、不同角度的缺陷发现、条件性结果协议，以及 `--fix`、`--comment`、`--max-findings`。因此 **333 的本地审查首先对齐新版 `/code-review`，只为“Ultra 级深审”增建多代理独立验证与复现**，避免重复开发已存在的本地审查功能。

同时，2.1.310 的 `/review` 是 `/code-review` 的别名；`/code-review ultra`、`/ultrareview` 和顶层 `claude ultrareview` 仍执行云审查。实测 2.1.310 原始程序的 `claude ultrareview --help` 写明 cloud-hosted，且没有 `--local`。本地新增入口建议设计成 `/code-review --local-deep`（提议，未实现），不改写云端命令语义。详细代码级差分和恢复风险见《2.1.88-2.1.310-本地多代理工作流和代码审查逐项复核》。

**恢复风险**：目标版本 Workflow journal 的某些写入失败仅告警，不能以“存在 journal”认定安全续跑，333 需额外保障持久化与不确定副作用核实；当前构建中的远端 Agent 隔离也不得算作本地已通过能力。

**底线**：本地复刻的是**功能行为与输出质量标准**，不能仅把云 API 地址替换为 `localhost` 就声称完整迁移；云端私有运行器尚无可独立部署和验收的等效源码。

## 二、实际代码级证据

### 1. 已具备的本地多代理基础（333 主分支）

- `src/tools/AgentTool/runAgent.ts`：子代理执行独立的模型查询与任务过程。
- `src/tools/shared/spawnMultiAgent.ts`：同进程 / 多后端 teammate 创建、角色配置和环境继承。
- `src/coordinator/coordinatorMode.ts`：协调者模式与工具限制。
- `src/tasks/LocalAgentTask/LocalAgentTask.tsx`：本地代理状态、进度和磁盘输出。
- `src/tools/AgentTool/forkSubagent.ts`：通过配置/构建开关启用的会话继承/并发代理路径。
- 旧代码存在并不代表 333 当前能从源码独立构建；先解决构建及旧版对照，之后做改造验证。

### 2. 2.1.310 Workflow 的本地路径

- `chunk-2pjf4p7s.js:445–519`：脚本内部已有 `agent()`、`parallel()`、`pipeline()`、`workflow()` 调用模型。
- `:990–1016`：代理起步写入 journal 的 `started`、`failed`、`result` 等事件，配置为远端隔离时若当前构建不支持会明确抛错。
- `:1570–1664`：从本地 journal 及会话仓库恢复运行的分支。
- `:1694–1718`：`task_local_workflow_resume`、`local_workflow` 任务、agent controller 和执行结果收口。
- 官网版本记录：**2.1.154** 引入动态 Workflow；**2.1.260** 增强 `agent({schema})`；**2.1.269** 增加每次运行的可配置并发上限；**2.1.300** 调整转移后的恢复审批；**2.1.305** 修复恢复后重复跑已完成 pipeline/parallel 节点。

上述证据已经足以认定：**Workflow 逻辑存在本地执行路径，云端托管只是一类执行部署选项**。需要保留日志/恢复/权限等行为契约，而非重写一套与 2.1.310 完全不同的简易“多代理循环”。

### 3. Ultrareview 的云端耦合边界

- 旧版 `reviewRemote.ts:133–158`：先校验远端服务资格/连接前提。
- `:164–203`：记录云端运行环境标识和 BugHunter 运行参数；其中旧版默认 fleet size 为 5，属于**2.1.88 的旧代码事实**，绝不可据此推断 2.1.310 的默认代理数量。
- `:208–228`：PR 审查走 GitHub 引用，提交到远端会话。
- `:229–292`：分支审查先计算 merge-base，再将工作树打包上传云环境。
- 2.1.310 `chunk-j0tbz6ra.js:33731–33732`：Ultrareview 的用户描述直接写明 cloud session。
- `:34298–34355`：完成后借助 `/v1/code/github/post-review-comment` 等远端服务接口发布 PR 评论。
- 版本记录：**2.1.111** 首次声明云端并行多代理深审、验证；**2.1.120** 增加 CI/脚本无交互入口；**2.1.269** 调整服务端直接发布；**2.1.285** 更改 Git 部分克隆和工作树上传；**2.1.309** 引入工作区信任检查。
- 在已提取的 2.1.310 JS 模块和资源目录中没有发现可独立执行的 `run_hunt.sh` 云端审查调度程序，**不能假定掌握了服务端完整 BugHunter 实现**。

## 三、333 的统一本地实施架构

```text
用户 /review --local 或 /workflow
           │
           ▼
本地 Session Runtime + 统一工具/权限/状态/日志
           │
     本地任务调度器
           │
   ┌───────┼───────────┐
   ▼       ▼           ▼
扫描代理  逻辑审查代理  风险/边界审查代理
   └───────┼───────────┘
           ▼
独立验证代理（复现、测试、反例）
           ▼
去重/分级/证据复核
           ▼
本地 JSON/Markdown/SARIF 结果 + 可选 GitHub 评论
```

* **调用语言模型的地点，与执行任务的地点分别配置**：
  1. **本机执行 + 在线模型**：文件、Git、沙盒、Agent/Workflow、审查报告、任务日志均在本机；模型请求仍然将必要上下文发送给所选在线提供商，不能称完全离线。
  2. **全本机离线**：上述能力完全相同，`ModelProvider` 改接本地部署模型，禁用所有云 API/远端审查及插件同步。必须检验模型的工具调用、上下文容量和结构化输出能力满足契约；推理质量不能因“执行在本地”就自动与云模型等同。
  3. **用户显式选择云执行**：未来需要时增加 cloud adapter；与本地实现共享结果协议和权限，严禁静默上传项目。

* **审查本地化必须做到**：未提交工作树可直接审查；Diff 限定参考分支/提交、识别改名/删除/未跟踪文件；只读沙盒内执行测试，临时工作树隔离复现；每个发现须有文件位置、可重复触发步骤、预期/实际表现、风险等级、建议及验证状态。没有复现证据的发现明确为“待确认”，避免假阳性冒充已证实缺陷。
* **安全与资源**：并发上限、任务取消、CPU/内存/Token 预算、可信工具策略；代理默认关闭自动派生能力，未经用户明确要求不启动子代理；临时工作树、凭据及网络访问设置为最小权限，报告默认保存在本地。
* **复用**：所有 Agent、Workflow、Review 使用同一个 `task_id`、`run_id`、步骤 journal、模型能力描述、工具权限和结果接口，避免本地审查维护第三套调度器。

## 四、迁移步骤与验收标准

| 顺序 | 必须交付的工作 | 核验方法 |
|---|---|---|
| 1 | 从 333 原有本地 Agent + 2.1.310 工作流代码提取**可验收的行为契约** | 正确继承工具/模型/工作目录/安全约束；统一任务事件 |
| 2 | 建立本地 Workflow 步骤调度、预算及持久化 journal | 并发依赖、超时/取消、崩溃恢复后不重复副作用 |
| 3 | 将远端 Review 命令拆为**审查入口**与**执行后端** | `--local` 完全不调用云端创建任务/打包上传端点 |
| 4 | 将 Review 接到共享本地 Agent/Workflow 引擎 | 多维独立发现、二次验证、结果整合、失败复核 |
| 5 | 交付基于真实 Git 改动的审查报告及结果消费 | 代码位置可复现；JSON/Markdown/SARIF 一致；PR 发布需显式授权 |
| 6 | 以 2.1.310 官方用户可观察结果为对照，独立验收 | 含真实缺陷集、无缺陷集、权限负例、断点恢复、大仓库性能和网络隔离测试 |

## 五、建议新增验收用例（本地能力）

- L01：断网条件下本地 Workflow 使用已部署本地模型完成多个独立 Agent 任务。
- L02：禁止远端网络时，Local Review 可以审查尚未提交的 Git Diff。
- L03：模拟 Workflow 完成节点后进程崩溃；恢复后不再执行完成过的写操作。
- L04：三 Agent 同时编辑同一文件，需显式冲突检测、隔离与复核。
- L05：审查样例包含真实缺陷、无缺陷和伪缺陷；每条发现有验证标记与证据。
- L06：审查发现 PR 中有密钥或忽略文件，未经明确批准不上传/发布。
- L07：在线模型适配模式可以本地执行，但提示用户推理请求会传送必要上下文。
- L08：本地模型拒绝工具调用或结构化输出时，明确提示能力不满足，不能虚构通过。
- L09：大仓库多 Agent 资源上限、取消、清理、磁盘不足及任务恢复。
- L10：本地与云端执行环境共用报告结构，但来源与信任等级有区分。

## 六、最终判定

**建议在 333 的统一运行时中把 Workflow 作为本地核心，先复用新版 `/code-review`，再在其上增加 Workflow/Agent/校验器实现本地 Ultra 级深审。** 此方案将已存在的本地 Agent 基础和新版 Workflow 主干最大化复用，用户无需上传代码到云端沙盒即可执行多轮代码审查。若仍使用云模型，相关代码上下文会发给模型服务提供商；只有选择合格的本地模型并禁用网络依赖后，才成立“完全本地化”。

目前尚未实现或执行这些本地验收测试；此处 L01–L10 为原评估用例，新增双版本复核 L11–L16 参见《本地多代理工作流和代码审查逐项复核》和《验收与迁移矩阵》。L01–L16 均属验收设计，不能计算为通过。
