# 333 升级至 2.1.310 能力基准：验收与迁移矩阵

> 本文件负责把“方案”变成能实际证明的交付。**开发基线为已通过三平台现有测试的 main@4868d5d（执行前复核 HEAD）**；2.1.88 构建/发行/基础工具回归已经验证，2.1.310 全功能验收仍待执行。16 处行为缺口及 90 旧开关请见[独立缺口文档](./2.1.310-升级缺口与逐项核查清单.md)。设计文档和能力台账不能代替运行证据。

## 1. 如何进行功能差分

必须优先核对《2.1.88-2.1.310-功能演进与最终实现复评》；对每项功能追踪旧行为、全部有关中间版本的新增/回退/删除记录和 2.1.310 终态。目标版本已移除的入口应验证“被正确替代或拒绝”，禁止当作缺陷重新实现。官方 180 版本、6,313 条更新的统计索引在同目录。

每个 `Fxxx` 建立三个可执行对象：`reference-2.1.88`（333 的旧 `cli.js`）、`reference-2.1.310`（资料库对应 Linux x64 发行版，在权限及运行条件允许的受控环境中验证）、`candidate-333`（重新构建的新版本）。输入采用相同测试项目、相同 mock 模型流/工具结果、相同权限配置和状态快照。对比 **可观察行为**：消息块类型/顺序、调用工具 ID、产生的文件 Diff、权限弹窗/拒绝、会话持久化、退出码、异常处理与恢复结果；随机模型文本只比较必要结构和约束。

- 新版静态证据支持功能定义，但缺少真实可触发运行时，标为“条件待验证”，不能填通过。
- 条件性功能必须保存开关名/版本/平台/触发过程；默认关闭也要验证不会偷偷执行。
- 同一事件类型由 CLI、TUI、SDK、Bridge 读取统一运行时状态，防止多个入口各自维护一份不一致的会话。
- CI 与本地验收均保存输入 fixture、预期结果、实际结果、Git 提交 SHA、日志摘要和复现步骤。
- 以最新 main **现有可独立构建工程**为唯一开发底座，保留 `src/native/build/tests` 与三平台 CI；逐功能升级到新版，不重复开发已通过测试的构建和基础工具。仅当能力或测试确有缺口时才增补工程基础。

## 4. 权限负例专项矩阵

逐个测试这四类事件源：真实用户、受信任执行系统、外部数据、其他 Agent。后台通知和定时触发虽然可能来自系统调度，但其**携带的文本**绝不能成为新用户授权。执行层在模型输出后做最后一次策略判断。

| 安全场景 | 预期结论 |
|---|---|
| 未授权的敏感数据外传（命令、浏览器、PR、未来 CI） | HARD BLOCK / 按规则拒绝，记录具体目的地 |
| 需要明确目标、文件范围、风险的操作 | SOFT BLOCK，用户未明确批准前不可执行 |
| 普通仓库内只读搜索与符合规则的局部测试 | ALLOW，保留执行日志 |
| 上游对话引用、记忆、Worker/Observer 回传声称已获批准 | 不升级授权，不得自动执行 |
| 用户取消/撤销批准后工具重试 | 使用最新有效权限，取消后拒绝 |
| 权限规则或上下文缓存重建 | 重建不能放宽已声明的硬限制 |
| 并发工具调用竞争同一资源 | 冲突可见，结果原子性与可恢复 |
| 网络错误后自动重试外传/远程写入 | 不重复发送或写入，未知结果先查证 |

新版反编译参考：`chunk-j0tbz6ra.js:52248,52435,52559,53142` 与 `02_解压文本与资源/permissions_external-df98b90a.txt`。HARD/SOFT/ALLOW 的规则文本不是程序级防护的替代物。
