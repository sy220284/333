# 333：2.1.88 ↔ 2.1.310 本地 Agent、Workflow 和代码审查逐项复核

**复查日期：2026-11-01**。复查对象：333 的 2.1.88 Source Map 源码、资料库 2.1.310 Linux x64 全量可读 JS 模块、两版原始程序 `--version/--help`、官方 2.1.89–2.1.310 版本记录。**复查结果是方案校正与实施契约，尚未构成 333 升级代码的端到端通过证明。**

## 一、复查结论（修正原方案的关键判断）

**原定方向成立，但必须改变 Ultrareview 的实施方式：**

1. **本地多 Agent：复用旧版现存本地 Agent/Coordinator/Worker + 新版增强。** 2.1.88 已有本地运行基础；2.1.310 则补强 Agent 后台、模型继承、权限、SDK 状态、Fork、工作树与任务操作。不能把“新版本云 Agent”整体认作缺失的本地功能。
2. **动态 Workflow：2.1.310 已有本地执行与恢复源码，旧版只有早期残留/门控，不应按完整本地 Workflow 已存在处理。** 可迁移终态行为，但 333 并未因此自动具备可编译/可使用的新版 Workflow。
3. **普通本地代码审查：2.1.310 已有比 2.1.88 `/review` 明显更完整的 `/code-review` 功能。** 包含不同审查强度、分角度审查 Prompt、结果发现/报告接口、`--fix`、`--comment`、`--max-findings`、部分配置下的后台子 Agent。**必须作为本地审查基座复用；原提案“从零建设所有本地审查逻辑”过度重复。**
4. **Ultrareview：2.1.310 的 `/code-review ultra`、`/ultrareview`、顶层 `claude ultrareview` 仍指向云端深审。** 要在本地获得相同级别的多代理交叉审查，需要在新版 `/code-review` 基座上**补建独立校验、反证、多代理编排、证据合并及隔离复现**，没有本地现成的完整 BugHunter 私有服务可复用。
5. **功能存在 ≠ 必然可用**：Workflow 存在受构建开关、配置/模型、运行模式影响的限制；`agent({isolation:'remote'})` 在检出的新版执行分支直接报当前构建不支持。普通 `/code-review` 的 ReportFindings 工具和后台策略也受选项与环境影响，不可把某一路径描述为无条件默认启用。
6. **恢复可靠性有额外风险**：检出的新版 Workflow 日志部分 `append` 失败只写警告后继续、某些结果不可序列化则重跑。333 需要强化副作用操作的“外部结果核实”，在无法确认时暂停，不能仅照搬日志逻辑就宣称 exactly-once。

## 三、对新旧版本演进的修正索引

- **2.1.88**：已有本地 `/review` 和云 `/ultrareview`、多 Agent / Coordinator 相关源码；`WorkflowTool/constants.ts` 只有标识，不能据此认定完整 Workflow 可用。
- **2.1.111**：云端 `/ultrareview` 正式发布；**2.1.120** 增加 `claude ultrareview` 脚本/CI 入口。
- **2.1.147**：`/simplify` 迁为本地 `/code-review`，支持不同努力等级和评论；**2.1.152** 增加 `--fix`。
- **2.1.154**：引入动态 Workflow；**2.1.202** 加 Workflow 规模选择；**2.1.260** 加结构化 schema 能力；**2.1.269** 加每次运行的并发设置。
- **2.1.218**：本地 `/code-review` 使用后台子代理；`/code-review ultra` 在无交互会话不再静默变成本地审查。
- **2.1.223**：`/review` 成为 `/code-review` 别名；`ultra` 指向云端深审。
- **2.1.232**：高强度本地 `/code-review` 也使用后台 Agent；**2.1.274**：部分模型默认审查改用本会话的精简流程，不能以“调用次数”推断一定存在多 Agent。
- **2.1.285**：管理员关闭 Workflows 时，Code Review/Ultrareview 的许可与入口需独立判定；禁止把 Workflow 配置直接用作本地 Review 的统一开关。
- **2.1.288**：本地 `/code-review --max-findings`；**2.1.300** 与 **2.1.305**：Workflow 执行转移和恢复改进。
- **2.1.309**：CLI 云 `ultrareview` 增加工作区信任要求；本地 `/code-review` 与 `/verify` 的技能发现修复。
- **2.1.310**：本地代码检查、动态 Workflow、远端 ultra 三种行为需要分别签收；云托管 Review 和本地 Review 不能因名称相近合并进度。

## 四、对现有落地方案的必须修改

| 原先表述或隐含前提 | 复查后的修订 | 验收/设计影响 |
|---|---|---|
| 本地 Ultrareview 从零实现完整审查 | **先迁入 2.1.310 本地 `/code-review` 的差异选择、Review Prompt、审查等级、发现协议、`--fix/--comment`，再扩充多代理验证** | 缩小重复代码面，保留新版已有用户功能 |
| `/ultrareview --local` 或 `claude ultrareview --local` | **推荐新入口 `/code-review --local-deep [target]`（333 自研待实现），保留原 `/code-review ultra` / `claude ultrareview` 云执行语义** | 任何新增参数先建立 schema/帮助/CI/CLI 回归；不能声称原版已有 |
| Workflow 已有 local_workflow 所以可直接上线 | **先验证构建、注册、开关、权限，再移植/重构满足行为合同的本地引擎** | 未验证开关仅记 SOURCE_IDENTIFIED；关闭时拒绝，不能假装执行 |
| 工作流可随时切换远端隔离 | 当前构建分支明确拒绝 `agent({isolation:'remote'})`；远端独立后端需单独条件校验 | 远端不可用需明确报错，本地 workflow 不依赖远端 |
| Journal 存在即恢复安全 | 源码有 append 失败仅警告的行为；不确定副作用可能在重放时重复 | 升级方案必须在强持久化和副作用核实之上实现 |
| 代理多＝审查更好 | 本地 `/code-review` 也能以单上下文完成多角度审查，深度校验需要样本实证 | 相同模型/样本下统计缺陷召回、误报、复现率和成本 |
| 本地审查天然只读 | `--fix` 和 `--comment` 实际有写入和网络副作用 | 审查默认只读；修复/评论需分别授权和记录 |

## 六、最终实施依赖与验收闭环

**M0** 核对旧版 `/review`、新版 `/code-review`、`/code-review ultra` 及 Workflow 注册/开关、实际运行和构建；**M1** 统一任务/协议/权限；**M2** 升级多 Agent；**M3** 新版 Workflow 语义及持久化恢复；**M4a** 迁入本地 `/code-review` 终态能力；**M4b** 在相同本地审查核心上补多代理独立找错、验证/反证、去重与报告；**M5** 多入口、推理与执行位置分离、云端可选；**M6** E/L 测试和真实缺陷样本签收。

**不得改变**：原云端 `/code-review ultra` 和 `claude ultrareview` 语义；用户未经批准不得派生代理、创建定时任务、上传代码、修改工作树、发布评论；每个 PR 维持中文标题与描述。

**本次复查完成的是计划和验收契约修订；333 本地深度审查的业务实现与全量通过仍待实际提交和运行。**
