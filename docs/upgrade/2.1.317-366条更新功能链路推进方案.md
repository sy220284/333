## 分链推进与关单规则

1. **先修第 0 层资源和构建**：将 `build/restore-claude-api.mjs` 中仍指向 2.1.310 的 106 份旧技能哈希映射，迁移到来自官方 2.1.317 的逐字节可追溯清单；更新 `build/verify-bundled-assets.mjs` 的旧版本来源。对照 310 与 317 原始文件及路径，不以当前仓库哈希代替原版证据。完成 Linux/macOS/Windows 候选版重建。
2. **修策略共享底座**：C01/C02/C04 的 effort、未知模型、压缩窗口、提示词、权限判定、自动模式和受管策略全局行为先统一；每个变更必须检查普通、自动、受限、bypass、SDK、后台 Agent 六种消费者。
3. **修可执行工具与消息协议**：C03/C06/C11/C16 对参数、结果、异步取消/超时、Hook、权限优先级、API 网络故障码做“原版 → 候选版”真实执行差分，出现副作用时必须隔离测试目录。
4. **修会话与 Agent 生命周期**：C05/C07 逐一核对嵌套 `claude -p` 身份隔离、父子/团队模型努力度、恢复 transcript、标题、后台 Shell、同一会话消息有序性与退出清理。
5. **修技能/插件/MCP/调度**：C08/C09/C10/C17/C18 检查发现、配置、安装、执行、同步、回收六段；云端调用、Artifact/数据库权限等由真实服务端证据签收。
6. **完成体验与跨端**：C12/C13/C14/C15/C20 必须包含真实 PTY、读屏、重试动画、远程/IDE/网关/Slack 等对应宿主测试；原版未公开的服务端组件作为单独证据缺口，不用本地模拟代替签收。
7. **总签收**：每条记录写入源码位置、原版证据、回归测试、官方二进制对照结果、分支与提交号及验收状态；C19 无独立更新编号也必须通过。每轮跑 `tests/m1-317-chain-matrix.test.mjs`，全部阶段满足后再更新 `docs/upgrade/upgrade-coverage.json` 的 102/84 状态并处理 PR。
