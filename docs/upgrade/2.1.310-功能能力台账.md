## 三、登记及判定规则

1. **80 项是升级设计的用户能力核对范围**，不表示 80 项均首次在 2.1.310 出现。旧版同类机制如协调者、Dream、压缩、自动权限、/btw 不重复计作新增。
2. 表内“新版核查重点”若仅是功能测试目标，实施时须补具体新版本模块行号、可触发开关和版本行为；未确权时标记为 `SOURCE_IDENTIFIED`，不能称“新版对齐”。
3. 333 的 1,926 个源码 blob 中存在极短的占位文件；检查具体注册/调用链后才确认有能力。旧 `cli.js` 可启动与新的 `src` 可构建分别记录。
4. 每个稳定 `capability-id` 扩展字段：`old_anchor / new_anchor / flag / platform / permission / owner_module / test_ids / commit / status / evidence_url`。状态依次为：`SOURCE_IDENTIFIED -> CONTRACT_CONFIRMED -> IMPLEMENTED -> INTEGRATED -> TESTED -> ACCEPTED`，另设 `BLOCKED`。
5. 逐项至少有成功、异常、拒绝、取消、恢复场景中的适用用例；最终总数只统计 `ACCEPTED`。禁用/未触发不等于通过。
6. 改造时将本台账转为可机器读取的 `capabilities.yaml`，由同一数据生成核对表、CI 测试映射和进度面板，避免未来反复人工盘点。

**证据边界**：2.1.310 的 2,551 个模块和 140 份资源是原始取证资产；缺少目标环境和运行会话时，静态推断应标注验证状态，不虚构默认启用。
