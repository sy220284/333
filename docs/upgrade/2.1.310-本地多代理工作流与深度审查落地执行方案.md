# 333：2.1.310 本地多 Agent、动态 Workflow 与 Ultrareview 落地执行方案

> **版本**：2026-11-01；**目标仓库**：333；**原始基线**：主分支 2.1.88 Source Map 提取源码；**目标行为证据**：2.1.310 原始 Linux x64 程序、可读 JS 反编译包、官方 2.1.89–2.1.310 变更记录。**本文件是待执行工程方案，不代表已修改功能代码或已通过功能验收。**

## 0. 已确定的方向与边界

1. **本地多 Agent：复用、对齐、增强**。旧版本已有本地 Agent、Coordinator、Teammate、任务生命周期；不要再复制一个“云端 Agent 框架”到本地。
2. **本地动态 Workflow：直接落实新版已有的本地执行设计**。2.1.310 可读模块存在 `agent()`、`parallel()`、`pipeline()`、`workflow()`、`local_workflow`、journal、恢复/审批等执行路径。按最新版可观察的行为做契约迁移，避免另写简易串行任务系统冒充 Workflow。
3. **本地 Ultrareview：需要新建完整审查执行链**。现有本地代码负责准备/上传 Git 仓库、启动云审查、回传结果，真正的 BugHunter 审查服务是远端私有组件；不能把云端入口换成 `localhost` 就称已经完整迁移。重新实现用户可观察的“多角色发现—复核—验证—去重—报告”能力，复用同一 Agent/Workflow 核心。
4. **保留云能力但不构成依赖**。原 `/ultrareview` 的云端路径可保留作为显式可选后端；本地路径能够不上传 Git 打包数据独立工作。选择本地执行时可以仍调用用户配置的在线模型（此时请求上下文可能离开本机）；需要完全离线时再切换本地模型并验收。
5. **不提前宣称代码等价或性能等价**。上游云端 BugHunter 的完整运行脚本、私有服务策略和评审模型组合没有可独立运行的公开交付物。目标为功能契约和可验证审查质量的等效，而非声称取得云服务端代码。
6. **用户授权边界**：默认单代理/不运行新的后台任务；用户明确触发多 Agent Workflow 或本地审查后，才在该任务授权范围内派生执行角色。禁止擅自创建定时任务。

## 2. 架构：一套执行底座，两类任务

```text
CLI / TUI / SDK / IDE
         │
统一任务 API（start / status / watch / cancel / resume / result）
         │
packages/runtime：任务状态机、队列、事件序列、预算、持久化
         ├──────── packages/agents：角色、子任务、模型/工具/权限继承
         ├──────── packages/workflows：脚本校验、依赖图、parallel/pipeline、
         │                              阶段审批、checkpoint、resume
         └──────── packages/review：Git 快照、Diff、审查编排、缺陷验证、合并报告

                   本地工作树/受控沙盒
                         │
     packages/providers：在线模型 或 用户指定的本机模型
                         │
     本地报告 JSON / Markdown / SARIF；可选显式 PR 评论
```

## 3. 本地多 Agent 的完整契约

- **任务申请**：由明确的用户任务发起；每个 Agent 具有不可混用的 `task_id`、`run_id`、`parent_id`、`agent_id`；关联用户授权的工作区、模型、工具及预算。
- **并行**：在预算内启动独立代理、读取实时状态和进度，所有结果以任务 ID 归档；具体并发额度为配置而非硬编码在 Prompt 里，超限排队并给出原因。
- **角色与权限**：子代理继承父级权限的交集，扩展/Mod/Prompt 无权放宽策略；敏感文件、外发和写入各自独立授权。拒绝产生清晰事件，禁止静默绕过。
- **冲突与隔离**：只读代理共享快照；需改文件的代理使用独立工作树，回收时检测冲突，由协调者选择重试/合并/退回用户，绝不覆盖用户未提交内容。
- **结果**：返回内容、使用的工具与模型、来源、耗时、失败原因、日志及真实验收状态；不接受“代理说已测试通过”作为最终证据。
- **终止和恢复**：取消通知必须传达给所有子任务，清理本地执行和资源；恢复时重建可核查的任务拓扑。已结束任务的历史可查询。

## 4. 本地动态 Workflow 的完整契约

必须支持：工作流的明确定义/名称与参数、`agent(prompt, opts)`、`parallel`、`pipeline`、受限的 `workflow(name)` 子流程、结构化返回与验证、步骤依赖、阶段状态、权限审批、持续进度、失败/取消、任务恢复；按目标版本验证实际限制（比如子流程嵌套层数、feature flag、平台限制），不能自己推定无限递归或默认启用。

### 4.1 运行日志及不重复操作

持久化事件序列至少有 `run.created`、`step.started`、`step.result`、`step.failed`、`step.cancelled`、`run.completed`；写入关联操作指纹、工具调用 ID、步骤输入哈希、目标快照版本和副作用确认标记。

- **已持久确认完成的纯计算步骤**：恢复直接读取结果；保持参数/脚本版本一致才命中。
- **尚未启动的步骤**：继续按依赖条件调度。
- **已启动但结果未确认的读操作**：可在相同权限与快照条件下重试。
- **已启动但结果未确认的文件写入、Git 提交、发布/评论等副作用**：先检查外部事实或幂等键；无法确定时转为 `NEEDS_RECONCILIATION`、暂停重放并提示可操作的检查路径。不得贸然再次执行。
- **日志写入或磁盘不足**：任务失败或暂停并报告；不能丢 journal 仍显示成功。
- **取消与审批**：恢复不继承失效的一次性批准，不允许靠老会话记忆扩大权限。

这一设计解决“进程在外部动作成功后、写日志前崩溃”的根因；对没有事务/幂等支持的外部操作，任何系统都不能空口承诺严格 exactly-once。

## 5. 本地 Ultrareview：需要重新建设的完整执行流程

### 5.1 用户可见行为

规划入口为 `/ultrareview --local [PR或分支]` / `claude ultrareview --local [target]`（**提议的参数，目前未实现**）。现有云端入口可继续使用，独立标记 `cloud`，避免静默改变原命令后端。实际 CLI 参数与 2.1.310 参考程序逐项对照后最终确定。

1. **选定快照**：识别 Git 工作区、base/merge-base/HEAD、PR 比较范围、改名与删除；读取尚未提交的受控改动。默认不纳入忽略文件与密钥，不擅自把未跟踪敏感文件送入模型；需要扩展范围时显式选择。
2. **构建审查计划**：识别语言/构建配置、增量变更、调用链和高风险区域；基于改动的依赖关系分组，避免一味按固定行数切块导致跨文件问题遗漏。
3. **并行独立发现**：按需分配逻辑正确性、边界/并发、安全与权限、兼容/接口、测试及迁移影响等角色。根据工作量选数量，预估模型调用预算；同一缺陷可由多视角交叉发现。
4. **候选问题标准化**：每条候选需记录精确文件/行范围、触发条件、预期与实际行为、风险、证据、建议、生成代理及关联提交；没有证据的猜测不得自动升级为已证实。
5. **独立验证与反证**：由不同角色核对调用链、执行受控测试或最小复现、检查反例；区分已复现、静态证据明确、待验证、误报。验证失败如实落状态，禁止声称通过。
6. **去重与结论**：合并根因相同的报告，按可复现性、影响范围、严重性排序；跨文件问题串联调用链；无发现报告附审查范围和测试覆盖边界。
7. **报告及交付**：本地 Markdown、JSON、SARIF、UI Diff 位置统一引用同一个结果 ID；可在用户批准后发布 PR 评论。报告带运行 ID、仓库快照、模型与执行环境、验证清单。
8. **恢复与取消**：审查可以查看进度、停止并恢复；恢复重用已确认结论并重新确认版本差异，避免把上次仓库的行号或证据错贴到新提交。

### 5.2 沙盒与隐私边界

- **默认审查只读**。测试在临时/隔离工作树中运行；任何自动修复、提交、推送或发布需单独授权。
- **本地执行 ≠ 本地推理**。在线模型需要发送最小必要文本，界面必须显示数据目的地与提供商；严格禁止云端代码仓库打包/云执行端点，不能阻止用户显式配置在线推理。
- **完全离线模式**：使用本机模型、网络出口限制、无云端 MCP/遥测/Artifact/插件同步；实际扫描网络请求验证，不可仅凭配置声明离线。
- **高风险输入**：仓库文件、PR 评论、测试输出是低信任内容，必须防提示注入、路径穿越、越权命令和密钥泄露；日志与报告脱敏。

### 5.3 审查结果数据模型（概念）

```yaml
review_run:
  run_id: "..."
  engine: local
  inference_location: local_or_online
  repository_snapshot: "commit-and-worktree-fingerprint"
  base_ref: "..."
  status: queued_or_running_or_completed_or_failed
  budget: {max_agents: 0, max_tokens: 0, max_duration_s: 0}
findings:
  - id: "stable-fingerprint"
    path: "src/example.ts"
    range: {start_line: 1, end_line: 1}
    title: "..."
    severity: "critical|high|medium|low"
    confidence: "high|medium|low"
    validation: "reproduced|source_confirmed|unverified|rejected"
    evidence: ["verified artifact refs"]
    repro_steps: ["..."]
    root_cause: "..."
    suggested_fix: "..."
```

> `budget` 为每次运行实际配置的数值；示例 0 表示尚未填写，不是默认值。严重性和验证状态分别表示影响与证据，不能混为一个分数。

### 质量验收的客观办法

建立**版本化缺陷样本库**，包含多语言项目及跨文件逻辑、安全边界、并发、兼容性、无缺陷样本；每个样本保存固定 commit、已知真实缺陷与可执行复现。对每次审查统计召回、误报、可重复率、总成本、延迟、并发资源占用；先测同样模型/相同上下文/相同样本的参考版本，再定可比较的目标和容忍波动。不能以报告条目变多作为质量提升。所有关键安全/权限负例要求 100% 通过；业务审查质量需要参考测试集上的实际证据，不臆造性能百分比。

## 8. 工程台账、回滚和交付定义

- **状态枚举**：`SOURCE_IDENTIFIED → CONTRACT_CONFIRMED → IMPLEMENTED → INTEGRATED → TESTED → ACCEPTED`；失败回退状态并附根因/可重放证据。
- **机器读取的单一事实源**：迁移方案落地后建立 `capabilities.yaml`、`scenarios.yaml`，由同一数据生成 F/E/L 测试映射和进度，避免重复手工统计。
- **追溯**：每项功能记录 2.1.88 函数入口、2.1.310 证据、目标模块、代码 commit、正/负/中断/恢复测试、报告路径和签收人。
- **回滚**：本地 Reviewer 后端与现存云 Reviewer 后端独立选择；代码/数据迁移支持安全回退，不清理用户现有项目/任务日志。回滚不跳过新版权限限制。
- **完成定义**：真实可构建代码＋用户可见入口＋完整任务闭环＋本地报告＋断网/在线模型分流＋全项验收通过；PR 合并或文档通过均不能替代此标准。
