## 1. 重评发现：旧方案应该更正的地方

1. 此前《80 项能力台账》按功能名盘点，缺失 `2.1.89—2.1.310` **180 个版本、6,313 条更新记录**的历史链路，无法判断功能是新增、变化、回退还是已废弃。见《逐版本变更索引》。
2. **先做版本演进差分，再谈架构**。不能一上来把 333 全面重写成新产品；333 现有 `src/` 是旧版参考实现，保留并用于对应功能语义和算法追踪，2.1.310 反编译 JS 承担终态取证，再做具体差异实现。可独立编译的工程化目标仍然必要，但它服务于行为一致性，不能以重构冒充升级。
3. 旧源码中有 2.1.310 已删除/废弃的功能入口；不可原样迁移。
4. 官方 Changelog 的 `Added` 可能是把已有功能开放到新平台，而非首次发明；例如 Monitor 在 2.1.98 已存在，在 2.1.310 扩展到更多模型提供者。所有新增声明必须写清 **首次出现/扩大支持/行为调整**。
5. 有些 2.1.310 代码由功能开关、环境、账户或运行入口决定，静态源码存在只表明“有能力路径”，不表明每个普通用户默认可用。

## 4. 对先前升级方案的修正

**原方案**以“独立工程完全重建”为先决条件，容易将已有功能重写一遍，又遗漏被替换的终态行为。修订后：

**第一步，冻结来源和版本链**：333 2.1.88 的 1,902 份 src 源文件、package.json、cli.js、原生模块作为旧版参考；2.1.310 的 2,551 JS 模块和 140 份资源作为终态证据。建立按功能编号的旧/新版/过程链接。

**第二步，按最终有效功能做差分**：优先解决 Monitor、Workflow、Mods/Hook、自动执行/权限、后台任务状态、Artifact、跨模型服务兼容、TUI、SDK/Bridge、会话与记忆；基础 Read/Edit/Grep 等已有项只补改变的语义和缺失的真实调用。

**第三步，可独立构建的工程体系**：恢复项目必需的合法构建依赖与适配层，在保持 333 原有用户功能的前提下拆分可测试模块；新代码由统一工具登记/状态/权限驱动，不能通过切换技术栈改变原功能行为。

**第四步，完整链路验证**：每项从官方版本记录得到“终态功能契约”，从反编译代码得到注册入口/调用/限制，再经过 333 源码实现和可触发的实际差分测试签收。被删除的功能按“替代/退场”验收，不以其缺席报缺失。

**第五步，可复用机制**：机器版本索引 + 80 个稳定能力 ID + 45 个端到端场景保持互相关联；每次新版本只需解析新增版本记录并核查受影响模块，避免完整推倒重盘。

## 5. 验收必须分清的四种状态

| 状态 | 证据 | 可对外宣称 |
|---|---|---|
| V1 版本记录定位 | 版本号、官方发布记录链接 | 知道哪个版本改变了什么 |
| V2 终态源码定位 | 文件、行号、条件、工具注册或调用 | 了解 2.1.310 静态实现路径 |
| V3 新代码对齐 | 333 新实现、运行入口、测试 | 已移植/实现指定功能 |
| V4 运行差分签收 | 相同场景下 2.1.310 和 333 行为证据 | 功能真正对齐 |

当前已完成 V1 的全版本目录统计，并有关键能力的 V2 静态证据；没有取得全部 80 项的 V4 对照。每条新旧版本差异需逐项完成 V2–V4，再计算交付完成度。
