## 工程根因和处理顺序

1. **先共享协议，后业务报错**：优先 `types/message.ts`、`types/tools.ts`、SDK 事件和配置类型。它们是大量 TS2307 与 TS2339 的共同源头。利用原版真实构造与消费者进行字段级推导，不用 `any`、`@ts-ignore` 或空接口。
2. **先确认运行可达性，后重建**：缺失模块的 `import type` / 动态 `import()` / `require()` 应区分。旧版 `HISTORY_SNIP`、`CACHED_MICROCOMPACT`、`CLAUDE_CODE_VERIFY_PLAN` 等编译门控须对照当前发行 `Bun.build.features` 和目标版行为，不应因 TS2307 就恢复已废弃实验代码。
3. **恢复真实功能链**：仍在目标版使用的模块按输入、输出、权限、状态转移、错误、取消、持久化和性能约束实现。可从原版函数消费者与新版反编译函数交叉定位；同名缺失/同名存在都不是终态证据。
4. **跨 PR 协同**：PR #9 负责实际公共类型、依赖升级和检查门禁；本 PR #7 负责双版本能力最终语义。PR #6 在 M1 全量验收前保持冻结。

## 验收要求

- PR #9 最新提交：全量 TypeScript 0 诊断、依赖安全审计 0 高危（目标为全等级 0）、三平台构建和差分行为回归。
- 本 PR M1：90 种旧开关的目标终态、61 项能力真实入口到结果链、6,313 条更新归属全部查证。
- 任何“源码已恢复”条目必须附源路径与消费者、实现提交、专项运行测试；缺源重写必须附原版/目标版行为比较，不以 CI 绿灯自动签收功能。
