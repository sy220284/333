# Super Agents 3.0：通用自主 AI 团队架构方案

> 设计基线：PR19（2026-11-07）；状态：已批准为实施目标，工程进展按实施清单逐项确认。产品本地优先，不引入自建云服务。

## 一、产品目标与边界

用户提出目标和授权边界，总控负责理解任务、动态组织团队、匹配模型与工具、发现并解决能力缺口、监控进展、核查成果、沉淀可复用经验。适用于软件开发、调研、视频剪辑、文案、设计、数据分析和跨专业项目。

持续保留两种模式：主子执行（有限目标、短期委派）与 Super Agents（长期项目、任务簿、具名成员、跨团队交接）。它们共享 AgentTool、Team、SendMessage、Workflow、Mission Job、SDK 会话及权限，不复制第二套模型执行器。

核心成功标准：用户可以让长期团队完成一次跨专业项目；系统发现缺少的能力时，能够产生可测试的扩展候选；发布后所有成员都能通过同一能力目录发现、授权调用；团队在关闭会话之后依然能基于已验证的知识和成果继续工作。

## 二、总体组成

| 层 | 组成 | 职责 | 复用 |
| --- | --- | --- | --- |
| 总控 | Project Supervisor | 目标理解、计划生成、变化检测、纠偏、验收 | Coordinator + Mission |
| 团队 | Agent Registry / Role Assignment | 稳定身份、动态角色、独立执行会话、跨项目角色能力 | AgentTool / Team |
| 协作 | Event Hub / Handoff | 对话、依赖通知、确认收到、工作交接、阻塞升级 | SendMessage / teammateMailbox |
| 能力 | Capability Registry / Builder / Validator | 统一发现工具、技能、插件、MCP、Workflow、模型能力；AI 生成扩展 | Tool / SkillTool / Plugin Loader / MCP |
| 结果 | Artifact Hub | 视频、图像、设计、文案、报告、代码的版本与验证证据 | SDK 产物、Git Worktree |
| 经验 | Experience Memory | 原则、规范、适用条件、可复用步骤、验证证据及失效条件 | 本地任务历史 + 检查点 |
| 客户端 | Team Chat + Board + Capability Center | 一屏内对话、团队列表、任务、成果、权限和能力详情 | Electron / desktopHost |

**单一事实来源**：Mission Job 决定工作项执行终态；Team Mailbox 决定原生交接投递状态；SQLite 用于事件、能力与经验索引；成果文件保存在项目目录，数据库只记录引用与哈希。迁移期用投影读取原有状态，逐项切换权威写入路径。

## 三、动态组织：身份与角色解耦

一个 Agent Profile 永久拥有稳定 ID、名称、历史专业能力和已核验经验；Role Assignment 随任务变化，可被重派、暂停、交接。执行会话、工作树、当前模型属于一次 Attempt。关闭会话不删除 Agent Profile。

默认能力模板包括总控、研究、创意策划、文案、视觉设计、视频剪辑、音频、开发、测试、审计；模板仅用于初始匹配，不决定最终团队人数。总控在每次规划时按任务产物、能力、资源、成本、依赖、历史成功率挑选或重配成员，尽量复用已有 Agent，不为简单任务强制并行。

团队内与跨团队交接统一为结构化 Handoff：
发起 → 已存储 → 已送达 → 已确认 → 已接受 → 执行中 → 已交付 → 已验收。
消息带 eventId、projectId、from、to、taskId、artifactRefs、reason、expectedOutput、deadlinePolicy、version，并以事件唯一号去重。向 UI 成员通知接口变化，向剪辑成员通知素材完成，属于同一消息和依赖机制。

## 四、主动总控的工作循环

1. 收到用户目标、项目文件变化、工具执行结果或已经授权订阅的外部事件。
2. 增量分析相关目标、已完成成果、资源预算、未解决问题与依赖。
3. 生成有证据和影响范围的 Observation；相同根因合并，避免重复派工。
4. 决策：回复用户、补充研究、安排现有成员、创建待审批工作项、寻找/开发新能力。
5. 根据授权的边界调用 SDK 及能力；人机共同处理必要审批。
6. 对真实文件、日志、测试和预览执行验收；失败时回退到产生问题的成员或步骤。
7. 更新任务事实，提炼规范与经验，整理有期限的待验证问题。

Github PR、CI、Issue、文件变更、视频质量检查、设计评审、文案校对、市场数据更新均映射到同一事件模型。监听源必须由用户逐个授权；本次升级不自动建立定时任务。运行中的本地宿主可以事件驱动工作，重启后以游标追溯并核查外部副作用。

## 五、统一能力中心

能力按 Tool（原子操作）、Skill（任务方法）、Plugin（组合封装）、Workflow（有阶段的执行图）、MCP（协议执行器）、Model（模型能力）、Bundle（专业能力包）分类。

每项能力以稳定 ID + 版本描述：
name、kind、source、scope、description、inputs/outputs JSON Schema、invocation、platforms、permissions、dependencies、manifest hash、tests、lastVerified、lifecycle、ui contribution。

已有能力：读取本地及插件 Skill 命令、启用的插件/内置组件、当前各作用域的 MCP 配置、原生工作流，统一在 Capability Registry 中投影为目录，原有加载器继续做执行器。目录包含来源与启用状态；配置存在不等于工具运行成功。

AI 自创能力的完整生命周期：
需求分析 → 检索已有能力 → 复用或组合 → 缺口说明 → 选择 Skill / Workflow / Tool / Plugin → 在独立目录构建 → 依赖/权限检查 → 静态扫描 → 行为测试 → 生成受限 UI → 待批准 → 发布到注册中心 → 加载与烟测 → 记录版本 → 后续改进与回滚。

自创 Tool 优先走本地 MCP stdio/HTTP，Skill 走原生技能目录，Plugin 走现有 manifest/loader，Workflow 走既有执行器。仅核心宿主需要直接访问的能力进入编译型 Tool。用户对能力版本、文件目录、可用网络、调用次数、费用及外部操作范围授权；模型不能因自己生成插件而获得更高权限。

扩展 UI 提供两级：标准 JSON Schema 自动表单及输出预览；复杂视频时间轴、画布、节点编辑器采用受控 iframe/独立渲染器与版本化消息协议。UI 模块无直接 Electron 主进程权限，所有工具调用仍通过受控 Host。

## 六、记忆是规范与经验，不是流水账

禁止把聊天记录、每轮工具调用或未经核验的自我总结直接当作长期记忆。原始执行日志仍可供审计，但不进入长期经验库。

经验条目必须包含：
- **场景与触发条件**：什么情况下需要这条知识；
- **原则或约束**：为什么这样做、需要遵守什么；
- **可复用步骤**：下一次具体怎么做；
- **适用与不适用边界**：版本、项目、工具和风险；
- **验证方法与证据**：实际测试、文件、提交、用户确认；
- **失败反例**：已证实的典型错误与避免方法；
- **状态和版本**：候选、已核验、已废弃；生效版本、审核人、复核时间。

工作会话结束后先从事实中抽取候选条目，再根据证据归并同义知识、发现冲突、审核和批准；只有已核验条目进入主动召回。项目级经验可在获授权后抽象成全局能力规范，保护敏感资料和项目边界。

**记忆提炼公式**：具体事件 → 抽象可迁移原因 → 可执行规范 → 验证步骤 → 失效条件。例：多次字幕偏移不是保存“今天又偏移”；应总结成“变帧率素材重定时先规范化时基并做首中尾三点对齐测试”，记录适用帧率、工具版本和失败样本。

知识更新采用版本化替代与冲突审查，过期知识不会静默覆盖新证据。召回按任务领域、场景、版本、权限过滤；限制篇幅，只向当前角色加载真正相关的规范。

## 七、交互设计：群聊主入口

左侧：项目、稳定 Agent 名册、团队群聊及私聊、最近任务。
中间：具名群聊消息，支持 @、引用任务、交接状态、实时进度、工具/能力发布、权限卡片与成果预览。
右侧：任务看板、团队进度、项目成果、能力中心、记忆规范、监督事件，可按当前消息自动定位，面板可折叠。
能力中心：分类、检索、来源、版本、权限、健康状态、已启用与待审核；点击能力使用 schema 自动生成配置表单与多模态预览。
保持现有 cc-haha UI 的有效主题与已联通的十类页面功能，不复制 Grok Bot 品牌和源代码资源；视觉上借鉴轻量群聊、清晰头像、低对比材质、动效和响应式抽屉。

## 八、授权、运行与交付

- 用户明确选择项目、可监控事件源、工具/插件启用和外部执行权限。
- 自创代码运行在隔离目录/进程中，使用最小文件和网络权限；安装需依赖清单和可验证哈希。
- 项目共享预算、同项目并发上限、暂停、取消和崩溃恢复沿用现有原语；长任务续接先核对真实副作用。
- 交付必须回到任务要求：视频实际可播放导出、文案可编辑比对、设计可预览、研究可查来源、代码有提交及验证；多智能体对话不算交付。
- 各类数据本地保存；不得以“保存了过程”冒称“学会了规范”。

## 九、验收基准

1. 跨领域任务动态配队且只派出实际需要的成员。
2. A 成员产生新版本后，B 收到有依据的交接、确认并完成调整，总控能追踪。
3. 现有 Skill、MCP、Plugin、Workflow 出现在同一目录，UI 数据取自真实后端。
4. 新建 Skill 或 MCP 工具经测试、批准后能注册并在 UI 中出现，重启后可复用；失败插件保持未启用状态。
5. 经验候选不能未经验证直接写为规范；重复经验能合并，废弃版本不会在检索中出现。
6. 进程中断、任务恢复、权限回传、项目隔离、版本回滚与成果验证保持正确。
7. Windows/macOS/Linux 的类型、构建、SDK 协议、安装版和至少视频/文案/设计/研究/代码端到端样例均有真实测试证据。

参照：Grok Bot 长期团队、独立角色及共享工具；ChatGPT Dot 主动工作、跨会话记忆与审批；DeepSeek dsh 原型的任务票据与授权分离。这里只借鉴可验证的行为和交互方式，功能实现及可用性一律以 333 代码、测试和真实环境结果为准。
